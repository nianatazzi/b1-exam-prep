## Порядок реализации фичи
Строго последовательно. Не переходить к следующему шагу без подтверждения:
1. Model
2. Repository
3. UseCase (если нужен — см. ARCHITECTURE.md раздел 3)

После завершения каждого шага — сообщить что готово и предложить следующий шаг.

## Правила слоёв

**data/** — только работа с Firestore. Никакого UI-кода. Никакого `BuildContext`.
Исключения Firestore маппятся в `AppError` здесь, до `domain` не доходят.

**domain/** — только бизнес-логика. Никаких зависимостей от Flutter или Firebase.

**presentation/** — только UI и провайдеры. Никакой прямой работы с Firestore.
Данные только через `ref.watch`. Логика только через `ref.read` в обработчиках событий.

---

## Правила моделей

- Все модели — `freezed` + `json_serializable`
- Обязательно: `fromJson`, `toJson`, `copyWith`
- `id` всегда из `DocumentSnapshot.id`, никогда не из тела документа
- `toJson()` никогда не включает `id`
- Nullable-поля помечаются `?`
- Enum вместо строк там, где есть закрытый список значений

---

## Жёсткие запреты
- Не хардкодить строки интерфейса — только ARB (`lib/l10n/`)
- Не хардкодить пути Firestore — только `FirestorePaths`
- Не хардкодить цвета, размеры, отступы — только `ThemeData` / `AppSpacing` / `AppSizes`
- Не использовать `catch` без маппинга в `AppError`
- Не подключать новые пакеты без явного указания
- Не хардкодить Firebase конфиг и ключи — только через `--dart-define` или `.env`
- Не использовать `StreamBuilder` без кэширования — лишние reads Firestore
- Не проверять роль пользователя только на клиенте
- Не писать Firestore-запросы внутри виджетов
- Не хранить `BuildContext` в репозиториях или провайдерах
- Не генерировать код для нескольких файлов сразу без явного запроса

## Работа с ветками Git
- **В самом начале каждой сессии** — первым делом проверить текущую ветку (`git branch`) и при необходимости создать feature-ветку. Не приступать к коду без ветки.
- Всегда работать в отдельной ветке. Никогда не коммитить напрямую в master.
- Название ветки: feature/короткое-описание
- Если ветка для текущей задачи уже существует — продолжать в ней, не создавать новую.
- При работе локально — не делать коммит сразу после завершения задачи. Сначала пользователь проверяет фичу через Run и убеждается, что всё работает. Только после явного подтверждения — делать коммит и пуш.
- Не делать merge в master самостоятельно — только через Pull Request.
